# M03 행성간 항해 모델과 통합 계약

도메인 버전 `transfer-1.0.0`. `src/transfer/`는 기존 M01/M02의 `src/sim` 계약과 저장소를 바꾸지 않는 별도 모듈이다. 이 문서는 계산·운영·저장 구현을 설명하며 UI 통합 및 최종 시각 QA 완료를 의미하지 않는다.

## 기본 사용

```ts
import {
  createTransferPlan, trySolveTransferPlan,
  createTransferRuntime, advanceTransfer, getTransferTelemetry, getTransferResult,
} from './transfer';

const plan = createTransferPlan('balanced');
const solved = trySolveTransferPlan(plan, craftDesign);
if (solved.status === 'solved' && solved.evaluation.launchable) {
  const runtime = createTransferRuntime(solved.solution, craftDesign);
  advanceTransfer(runtime, simulatedSeconds, 500);
  // Worker에서는 진행률을 보낸 뒤 yield하고, 남은 요청 시간을 0초 입력으로 소진한다.
  const telemetry = getTransferTelemetry(runtime);
  const result = getTransferResult(runtime);
}
```

`trySolveTransferPlan`의 수치 해 성공과 `evaluation.launchable`은 별개다. 물리적으로 풀린 경로라도 단계 추진제·예산·페어링 위반이면 실행은 막힌다. `solveTransferPlan`은 오류를 던지는 하위 API다. 계산 결과는 함수나 클로저가 없는 JSON이며 Worker 사이에 복제할 수 있다.

`advanceTransfer`는 요청 시간을 누적하고 완성된 결정론적 구간만 처리한다. 요청이 다음 구간보다 짧으면 `requestedTime`과 실제 `time` 사이에 나머지가 남는다. `maxSteps=500`씩 실행하면 UI 진행률을 자주 갱신할 수 있다. `advanceTransfer(state,0,500)`을 반복하되 시간이 더 진행하지 않으면 현재 요청에 대해 완료된 상태다. `state.status`가 종료 상태이면 멈춘다. 전체 미션 preview는 검증 환경에서 약 수 초이며 메인 UI 스레드 대신 Worker에서 실행해야 한다.

## 계획·프레임·경계

- 실제 JPL Horizons 지구/화성 위치·속도 2,313개씩을 로컬 JSON으로 묶었다. ICRF, 태양 중심, 기하 벡터, TDB, km/km/s다. 2026-08-01~2028-03-01을 6시간 간격으로 포함한다. 게임 실행 중 외부 API를 요청하지 않는다.
- `TRANSFER_DATA_SOURCES`와 테이블/행은 동결되어 공유 호출자가 자료를 바꿀 수 없다. 원자료 URL·조회 시각·SHA-256을 보존하고 저장에도 해시를 기록한다. Hermite 보간은 자료 범위 밖에서 실패한다.
- `FullTransferPlan`은 출발/도착 근지점의 Julian TDB, 지구 주차 고도, 화성 최근접 고도, 출발 평면 각, 실제 입사 점근선에 대한 화성 B-plane 각, 탈출 단계와 시간 지정 운영을 가진다.
- 지원 범위는 120~450일 비행, 주차 고도 200~1,000 km, 화성 최근접 250~10,000 km다. 기간을 바꿀 때 운영 일정도 함께 바꿔야 한다. 임무 종료 이후 일정은 실제 해의 종료에서 잘리고 `scheduleWarnings`/`SCHEDULE_CLIPPED`로 명시된다. 중첩 일정은 거부한다.
- 0회전 Lambert와 6변수 미분 보정으로 지구 경계·태양 순항·화성 경계의 위치/속도를 맞춘다. 지구/화성 경계 반경은 각각 924,000/577,000 km다. 그곳에서 지배 중력이 바뀌므로 가속도는 연속인 다체 모델이 아니다.
- `transferStateAt(solution, elapsedSeconds)`는 태양 기준 벡터와 현재 단계의 중심체 기준 벡터를 함께 반환한다. 단계는 `earth-escape`, `solar-coast`, `mars-flyby`다. `transferTrajectory(solution, phase, count)`는 포함된 끝점도 요청한 단계의 같은 상대 프레임으로 변환한다. 프레임이 바뀌어 마지막 점이 튀는 폴리라인을 만들면 안 된다.
- `phaseEvents`는 출발, 지구 경계 이탈, 화성 경계 진입, 최근접, 화성 경계 이탈의 실제 시각이다. 날짜는 TDB이며 UTC `Z`나 기존 M02의 TAI epoch로 바꾸어 라벨링하지 않는다.

## 단계와 두 성공 경로

탈출 단계의 모든 이름·가격·질량·Isp·페어링 한도는 게임 가정이다. 실제 제조사나 발사 사업자 성능으로 표시하지 않는다. 원형 주차궤도와 탈출 평면은 시작 시 정렬됐다고 가정한다. 지상 발사장 접근성이나 대기권 상승은 풀지 않는다.

| 단계 | 건조/추진제 | Isp | 최대 탑재 | 페어링 | 크레딧 |
|---|---|---:|---:|---|---:|
| Pathfinder | 28/240 kg | 330 s | 85 kg | 2.8×3.0 m | 95 |
| Explorer | 40/380 kg | 340 s | 110 kg | 3.2×3.6 m | 140 |
| Heavy | 60/600 kg | 350 s | 140 kg | 3.8×4.4 m | 210 |

실제 요구 C3를 원형 주차궤도 탈출 Δv로 바꾸고, 단계 건조 질량과 젖은 탑재 질량을 포함한 로켓 방정식으로 추진제를 계산한다. 단계는 이상적인 순간 기동 후 버려진다. 탐사선 자체의 6 kg 추진제를 그 기동에 사용한 것으로 처리하지 않는다. 비용 한도는 게임 크레딧 680이다. 페어링 검사는 실제 수납 OBB 외곽을 사용한다.

다음 두 조합은 전체 자원 운영과 지구 수신까지 실제 테스트에서 성공한다.

| 프리셋 | 출발→화성 최근접(TDB) | 최근접/B-plane | 단계/기체 |
|---|---|---|---|
| balanced | 2026-11-15→2027-08-02 | 1,000 km /0° | Pathfinder /Mars balanced |
| science | 2026-11-03→2027-08-15 | 1,500 km /45° | Explorer /Mars science |

이것은 유일한 정답을 강제한 보너스가 아니다. 경로·부품·태양 거리·지향·전력·자료 전송 계산 결과다. 창에서 벗어난 2026-08-15 출발의 같은 260일 경로는 Pathfinder 추진제 한도를 넘는다.

## 실제 환경과 자원

- 태양 방향과 거리는 실제 태양 중심 상태에서 계산한다. 발전은 기존 물리 장착 광선 가림·입사각·역제곱 거리와 실제 자세를 사용한다. 지구/화성의 태양 차폐를 검사한다. 고정 M02 태양 방향이나 고정 1.524 AU를 재사용하지 않는다.
- 지상 수신점은 교육용 5개국 네트워크와 근사 지구 자전을 사용한다. 실제 DSN 시간표나 정밀 UT1/EOP 모델은 아니다. 고정된 송신 위치에서 움직이는 지상국의 수신 위치까지 광속 지연을 반복 계산한다. 위상별 지구 방향·거리는 계속 달라진다. 최소 지상 고도각 5°, 태양 방향 3° 이내 교신 제한은 게임 운영 정책이다.
- X-band RF 5 W, 탐사선 35 dBi, 지상 66 dBi, 시스템 100 K, 기타 손실 3 dB, 요구 Eb/N0 4.5 dB로 실제 거리의 링크 예산을 계산한다. 이 값은 고정 교육 가정이며 제조사 인증값이 아니다. 데이터 전송률은 512~524,288 bit/s 범위에서 골라진다.
- 배터리 계산은 Wh, 부하는 W다. 충전/방전 효율과 EPS 한도는 M02와 같은 게임 정책이다. 4%에서 안전 모드, 16%에서 일정 복귀를 하며 임계점은 구간을 나누어 처리한다. 실제 자세는 20°/s로 회전하고 전환 중에는 실제 패널·관측기·안테나 방향을 쓴다. 발전 방향을 성분별 10⁻¹²로 정규화해 부동소수점 잡음을 제거한 동일 입력에서만 광선 결과를 재사용한다. 이 정규화는 UI의 텔레메트리 조회 순서와 무관하다.
- 순항 최대 간격은 600 s, 검증용 300 s도 지원한다. 초기 출발 3,600 s와 최근접 ±9,000 s는 5 s, 나머지 지구 탈출은 최대 60 s다. 작업 경계·상태 전환·수신·그림자·배터리 임계점을 따로 분할한다. 자세 전환은 최대 1 s 구간으로 해상한다.
- 화성에서 빛을 받는 지표 방향, 12,000 km 이내 거리와 분광기 시야를 검사한다. 품질은 장비 가시율과 거리로 정한 교육 지표다. 고유 300 s 구간의 자료, 최소 120 s 획득 간격, 24 Mbit/자료를 사용한다. 품질 0.4 이상 자료 3개를 지구에 완전히 수신해야 성공한다. 실제 스펙트럼 생성·노출 적분·지질 분류는 아니다.
- 수신하기 전 데이터는 저장장치에서 지우지 않는다. 송신과 수신을 구분하고 실제 광속 지연이 지난 완전 수신만 점수에 넣는다. 60 s RF 프레임을 사용하여 연속 구간에서 모인 비트를 프레임 끝에 보내는 보수적 수치 근사다. 추가 자료 지연은 최대 60 s이고, 이 프레임화가 수신 사건을 무한히 잘게 쪼개는 수치 문제도 막는다.

## 저장·복구

`makeTransferSave(plan,craft,runtime?)` → `serializeTransferSave(save)`를 사용한다. JSON에는 풀린 궤도 좌표가 들어가지 않는다. 모델·원자료 해시, 유효한 설계/계획, 선택적으로 자원·자료·자세·시각 체크포인트만 저장한다.

`parseTransferSave(text)`는 스키마·유한 범위·자료 해시를 검사하고 궤도를 다시 풀어 저장 시각까지 재실행한다. 연료·에너지·자료·신호·자세·틱·상태를 대조하며 조작된 체크포인트를 거부한다. 임시 설계는 물리적으로 실행 불가능해도 스키마가 유효하면 보존할 수 있다. 지원하지 않는 모델은 조용히 점수를 재사용하지 않고 거부한다.

`saveTransferLocal`은 별도 IndexedDB `orbital-foundry-journey`를 사용한다. UI 스레드에서 `loadTransferLocalText()`를 읽고 Worker에 `parseTransferSave`를 요청하면 긴 복구 동안 UI가 멈추지 않는다. 저장 트랜잭션 실패는 호출자에게 전달된다.

## 검증과 남은 제한

- 계획 테스트와 독립 감사: 실제 Horizons 원응답 해시, 별도 26개 보간 표본, 실제 GMAT의 경계별 2,317개 상태, 위치/속도 경계 연속성, C3 및 단계 질량 방정식, 자료 동결·프레임 일관성을 대조했다. 전체 별도 연구 GMAT 세트는 6개/4,084개 상태이며 기존 M01/M02 8개 세트와 섞지 않는다.
- 자원 테스트: 두 전체 미션 성공, 300/600 s 순항의 같은 과학 자료/점수 및 최소 에너지 오차 0.05 Wh 미만, Worker 분할 및 전송 중 저장 후 같은 자료/신호/이벤트, 조작된 저장 거부를 확인한다.
- GMAT 중심중력 검증은 실제 천체력/시계 변환, 모든 섭동, 단계 추진 상세, 통신 또는 게임 전체 완성도 인증이 아니다. [연구 제안과 증거 범위](earth-mars-transfer-proposal.md)를 함께 참고한다.
- 아직 순항 보정 기동, 실제 추력축 실패에 따른 계획/실행 궤도 분기, 지상 명령 큐, 반작용휠 토크/관성, 열 모델, 행성간 다체 섭동, 출발 평면 변경/지상 발사는 이 M03 런타임에 없다. 이 범위를 이미 구현한 것으로 발표하면 안 된다.
